================================================================================

Contract address: 0x0B660D66b05a743Df3755058c2e63d5a5f2bA2F7 (file: 0x0B660D66b05a743Df3755058c2e63d5a5f2bA2F7_flat.sol)
Project: Hegic Options (HegicOptions / HegicCallOptions / HegicPutOptions / HegicETHPool / HegicERCPool), pragma ^0.6.0
Issues and vulnerabilities:
- Reliance on a single Chainlink oracle via the deprecated priceProvider.latestAnswer() function, with no check for round completeness or staleness (no check of latestTimestamp or answeredInRound). If the price is stale or manipulated, both the premium calculation in fees() and the payout in payProfit() will be computed incorrectly. There is no fallback mechanism or price-deviation bound.
- In HegicPutOptions.sendPremium, the ETH-to-stablecoin swap is executed directly on Uniswap with amountOutMin derived from maxSpread, whose default value is adjustable up to 95%. This extremely large slippage tolerance leaves the transaction exposed to sandwich/MEV attacks on the public network and can let a front-runner capture a significant share of users' premiums.
- Centralization risk: the transferPoolOwnership function in HegicCallOptions and HegicPutOptions lets the contract owner, within the first 90 days, transfer ownership of the liquidity pool (HegicETHPool/HegicERCPool) to an address of their choosing (the current owner). After this transfer, the pool's onlyOwner functions (send/unlock/lock/sendPremium) become directly callable by the owner without going through the option contract's logic, so if the owner key is compromised the pool can be drained directly.
- Use of `now` (block timestamp) to compute option expiry is susceptible to minor miner manipulation (timestamp manipulation on the order of a few seconds) — a low but worth-noting risk.
- No explicit reentrancy guard (nonReentrant) on create/exercise/unlock; although the checks-effects-interactions order is largely respected, the multiple chained external calls (pool.send followed by unlockFunds) create heavy reliance on the correctness of the pool's own implementation.
- Critical functions such as setImpliedVolRate and setSettlementFeeRecipient are protected only by onlyOwner and can be changed instantly with no timelock; the owner could change the implied volatility rate in a way that suddenly and without warning alters the premiums users pay.

Contract address: 0x0e128fb9f266f0cfedeb3b789f6fd4af50d51b84
Project: Upgradeable proxy set (BaseAdminUpgradeabilityProxy, ProductProxy, InitializableProductProxy), pragma ^0.6.0
Issues and vulnerabilities:
- A classic "proxy initialization race condition" vulnerability: the function __InitializableProductProxy_init is declared public and is protected only by require(_factory() == address(0)), with no access-control modifier at all. Since factory is still zero after deployment and before the deployer calls init, anyone can front-run the init transaction and register their own factory; a subsequent delegatecall (via the data_ parameter) to an attacker-chosen implementation can then take over the proxy's entire storage (the same attack pattern as the well-known Parity wallet / several Value DeFi vault hacks).
- The _implementation function in ProductProxy depends entirely on the factory_ address (changeable in the same vulnerable transaction above) and the productImplementations(name) mapping; if an attacker takes over factory, every subsequent user call to this proxy will delegate to code of the attacker's choosing (full contract takeover).
- The base fallback function (_fallback) has a special condition for no-data ETH payments (gasleft() <= 2300) that, if the assumed gas amount forwarded by other contracts is wrong, can produce unexpected behavior (a silent return without delegating); a low but worth-noting risk for contracts that depend on correctly receiving ETH.
- The base EIP-1967 pattern (BaseUpgradeabilityProxy/BaseAdminUpgradeabilityProxy) correctly uses the standard storage slots, and no storage-collision issue was observed in this part.

Contract address: 0x13db1CB418573f4c3A2ea36486F0E421bC0D2427
Project: WarpVaultLP / WarpWrapperToken (Warp Finance), pragma ^0.6.0
Issues and vulnerabilities:
- No check of the return value of LPtoken.transfer/transferFrom (used directly with no require on the boolean output). For non-standard ERC20 tokens that return false instead of reverting on failure (as some older tokens do), provideCollateral could increase a user's collateralizedLP balance without any real token transfer taking place (value extraction without actually depositing collateral).
- angryWizard is a single global timestamp (timeWizard) that is set only once in the constructor and is never reset by any function in this contract; as a result the time restriction on _liquidateAccount is only enforced during the first week after deployment and is permanently disabled thereafter, rather than being a per-user or per-event restriction as its naming would suggest.
- Full control is delegated to warpControl (a single external contract): both the liquidation logic (_liquidateAccount, with an arbitrary _liquidator address supplied by warpControl) and the collateral pricing (viewPriceOfCollateral) come from this one address; if warpControl is vulnerable or compromised, arbitrary liquidation or collateral-valuation manipulation becomes possible (centralization/trust-chain-dependency risk).
- updateWarpControl is protected by onlyWarpControl, meaning only the current warpControl can replace itself; no timelock or multi-signature confirmation was seen for this critical change.

Contract address: 0x14413419452aaf089762a0c5e95ed2a13bbc488c
Project: Poly Network EthCrossChainManager / UpgradableECCM (Poly Network's cross-chain bridge), pragma ^0.5.0
Issues and vulnerabilities:
- A critical and well-known vulnerability in the whitelist architecture: after verifying a Merkle proof, verifyHeaderAndExecuteTx makes an arbitrary call via _executeCrossChainTx to any toContract address that is authorized in whiteListContractMethodMap. The changeBookKeeper function (which replaces the entire keeper set — i.e. the root of trust for the whole bridge) is defined in the very same EthCrossChainManager contract and is public. If this contract's own address, together with the changeBookKeeper method signature, is ever registered in whiteListContractMethodMap (whether by mistake on the whiteLister's part or for any other reason), an attacker can craft a fake cross-chain event whose toContract equals EthCrossChainManager itself, and through the normal verifyHeaderAndExecuteTx path replace the keeper set with a public key of their own choosing; posing as a legitimate "keeper" afterward, they can then withdraw any amount of assets locked in the proxies on other chains. This is exactly the abuse pattern behind the real-world Poly Network protocol hack (full keeper takeover).
- Neither changeBookKeeper nor initGenesisBlock has any onlyOwner or onlyWhiteLister access control — they are protected only by whenNotPaused; their correctness depends entirely on the logic of ECCUtils.verifySig and the signatures of the current keepers, meaning that if the multi-signature keys of the Poly Chain keepers (managed outside this contract) are ever leaked, the entire bridge is at risk with no other defensive layer.
- The required signature threshold (n - (n-1)/3, roughly a 3/4 majority) is hardcoded, and verifySig has no explicit check against duplicate signers unless this is implicitly handled inside containMAddresses; this uncertainty could reduce the real security threshold.
- The pause/unpause/upgradeToNew function is protected by onlyOwner, but owner is a single address (an EOA or a multisig outside this code); if the owner key is leaked, the bridge could be fully paused or maliciously upgraded to a new contract. No timelock or mandatory delay between upgradeToNew and its execution was observed.
- In _executeCrossChainTx, the external call is made with a raw call and a manually encoded selector (encodePacked instead of encodeWithSelector); while this usually works correctly in practice, using encodePacked to build calldata with dynamic, non-fixed-length parameters is susceptible to encoding collisions in certain scenarios.
- The use of tx.origin in the CrossChainEvent is purely for logging and is not used in access-control logic, so it does not by itself create an access-control vulnerability, but it can record misleading information (the real sender behind an intermediary contract) in its events.

Contract address: 0x17e8Ca1b4798B97602895f63206afCd1Fc90Ca5f
Project: Furucombo Proxy (a DeFi transaction combinator that delegatecalls into handlers registered in a Registry), pragma ^0.6.0
Issues and vulnerabilities:
- A fundamental architectural vulnerability (the pattern behind a real attack on this type of proxy): the fallback function only checks the identity of the direct caller (msg.sender) against the registry (_isValid(msg.sender)) and then, with no content validation at all, delegatecalls the entire received msg.data verbatim to the handler corresponding to that caller. Because this call happens from inside an external protocol's callback (e.g. a flash-loan callback) and the payload of that callback is determined by whoever originally called batchExec/execs, an attacker can craft a specific transaction combo so that, instead of the expected operation (e.g. settling a flash loan), the handler executes a token-approve call with an attacker-chosen spender in the proxy's storage/identity context. This is exactly the root cause of the real attack the Furucombo protocol suffered, which drained the approved tokens of all users of the proxy.
- The _exec function uses a raw delegatecall in assembly and executes the target handler's code in the full storage context of the Proxy contract (including the stack, cubeCounter, and stored sender); any bug or unexpected behavior in any of the dozens of handlers registered in the Registry can directly manipulate the entire storage of the proxy shared by all users (a very large, centralized attack surface in a single proxy contract).
- Neither batchExec nor execs places any restriction on what arbitrary handlers can do with tokens a user has approved; complete trust is placed in the correctness of every handler registered in the Registry (a separate external contract not present in this file) — in other words, the security of the whole system depends on the quality of Registry management, which was not reviewed here.
- In _postProcess, leftover tokens/ETH are returned to msg.sender under the assumption that msg.sender is the same user who originally initiated batchExec; if execs (the internal version callable only by the proxy itself) is invoked from within a handler with a spoofed msg.sender, this assumption could be violated, although require(msg.sender == address(this)) does somewhat prevent direct external calls.
- Use of msg.sender.transfer(amount) to return leftover ETH; this standard method forwards a fixed 2300-gas stipend, which can revert for contract wallets (such as multisigs or account-abstraction wallets) with heavier fallback logic, causing the ETH to become stuck in the transaction (a partial denial of service for some users).
- _trim uses raw assembly to directly manipulate input memory (data) based on offsets computed from configs; insufficient validation of the offset (only refs[i] < index is checked for the local stack, not validation of the offset against the actual length of data) could, given an incorrect or malicious config, lead to out-of-bounds memory reads/writes.

Contract address: 0x1f0d1927498fbd4f9e8558704ce5b658929527ec
Project: Zapper_Matic_Bridge_V1_2 / ZapBaseV1 (an Ethereum-to-Matic/Polygon bridge zapper with swaps routed through 0x), pragma ^0.5.0
Issues and vulnerabilities:
- A critical "arbitrary external call" vulnerability in _fillQuote: the swapTarget and swapData parameters are entirely determined by the caller (the user) in ZapBridge, with no whitelist or validation applied to swapTarget. An attacker can supply the fromToken (ERC20) contract's own address as swapTarget instead of the real 0x router address, and use the transfer(attacker, amount) method as swapCallData. Because this call is made from inside the Zapper contract (swapTarget.call.value(...)(swapCallData)), msg.sender inside the transfer call will be the Zapper contract's own address, so this operation — with no approval needed at all — directly transfers the Zapper contract's entire balance of fromToken (including accumulated goodwill fees and other users' not-yet-withdrawn affiliate balances) straight to the attacker's address. This is exactly the class of attack that several real Zapper and aggregator projects in DeFi have suffered losses to.
- In addition, _approveToken(fromToken, swapTarget), called before the swap, grants an unlimited allowance (uint256(-1)) to the attacker-controlled swapTarget address; even if the direct transfer path above is blocked, this unlimited approval to an entirely arbitrary address is, on its own, a large attack surface for withdrawing any future balance of fromToken in the contract, and it is never revoked since _approveToken only approves once and leaves it untouched afterward.
- withdrawTokens/affilliateWithdraw compute the withdrawable balance as the difference between the total balance and totalAffiliateBalance; if the contract's balance is drained by the attack above, this SafeMath subtraction can underflow-revert, effectively blocking even legitimate withdrawals by the owner/affiliates (a secondary denial of service after the primary attack).
- No reentrancy guard (nonReentrant) on ZapBridge/_fillQuote despite an arbitrary external call carrying ETH (swapTarget.call.value); combined with the issue above, this can produce more complex side effects (such as re-entering ZapBridge mid-processing).
- The goodwill fee is adjustable by the owner up to a value of 100, but _subtractGoodwill computes it on a base of 10000 (amount*goodwill/10000); this unit mismatch means the actual maximum configurable fee is effectively 1%, not 100% as the require statement suggests. While this is more of a logic/unexpected-limit issue than a direct security vulnerability, it can make the contract's behavior misleading relative to its documentation.
- The fallback function (direct ETH payment) is protected only by require(msg.sender != tx.origin), a weak and bypassable check (any intermediary contract can get past this condition) for its stated purpose of "preventing direct ETH sends."

Contract address: 0x20e5e35ba29dc3b540a1aee781d0814d5c77bce6
Project: OpenZeppelin upgradeable proxy set (TransparentUpgradeableProxy, ProxyAdmin, UUPSUpgradeable/Proxiable, ChildOfProxiable), pragma ^0.8.0
Issues and vulnerabilities:
- A critical "unprotected UUPS upgrade" vulnerability in the ChildOfProxiable contract: this contract overrides the abstract _beforeUpgrade function with a completely empty body ({}). Since UUPSUpgradeable's public, unguarded upgradeTo function calls _authorizeUpgrade directly, and in Proxiable, _authorizeUpgrade simply calls _beforeUpgrade, and in ChildOfProxiable this function has no require or onlyOwner check, the result is that upgradeTo/upgradeToAndCall is open to any external caller with no restriction whatsoever. Any address can change the implementation behind this UUPS proxy to a contract of its own choosing and take full control of the contract and all assets/storage behind it. This is exactly the same class of vulnerability behind several real-world UUPS contract hacks (forgetting to implement access-controlled _authorizeUpgrade).
- By contrast, the TransparentUpgradeableProxy/ProxyAdmin path in the same file is correctly protected with ifAdmin/onlyOwner following the standard OpenZeppelin pattern, and no specific security issue was found there; so the main risk in this file is specific to the UUPS path (ChildOfProxiable), not the Transparent Proxy path.
- General centralization risk: in the ProxyAdmin/TransparentUpgradeableProxy architecture, a single owner holds complete control over upgrading the implementation and changing the admin of all proxies it manages; no timelock or mandatory multisig was seen at this contract's level (a common design risk rather than necessarily a bug, but it becomes more significant in combination with the UUPS vulnerability above).
- If ChildOfProxiable was intended in production as a "base template for future implementations" that subsequent developers were expected to override _beforeUpgrade on with real access-control logic, the absence of at least a default require(false) or onlyOwner in the base implementation turns it into an insecure-by-default template.

Issues and vulnerabilities:

Contract address: 0x35c674c288577df3e9b5dafef945795b741c7810
Project: Memefund (an Ampleforth-style elastic/rebase token) + Memestake (a MasterChef-style farming pool), pragma 0.6.12
Issues and vulnerabilities:
- A critical calculation bug in Memestake.claimRewards: the pending amount in this function is computed as user.amount.mul(pool.accMfundPerShare).div(1e24), and rewardDebt is updated using the same scale (1e24), whereas every other function (updatePool, deposit, withdraw, pendingRewards) computes accMfundPerShare on a 1e18 scale. This scale mismatch means that after a single call to claimRewards, the user's stored rewardDebt becomes roughly 1,000,000 times smaller than it should correctly be under the 1e18 scale. As a result, the next time deposit or withdraw is called (which compute pending using the correct 1e18 scale against the now-incorrect rewardDebt), the computed pending amount becomes artificially enormous, and the user can withdraw far more MFUND than their actual share of the pool. This is a practical path for any user to unfairly drain some or all of the MFUND balance held by the Memestake contract simply by calling claimRewards once and then deposit/withdraw afterward.
- The add function in Memestake lets the owner add any arbitrary IERC20 contract as a new pool, with no check that the token has standard behavior (no transfer fee, no rebasing); lpSupply is read directly from pool.tokenContract.balanceOf(address(this)), so a fee-on-transfer or otherwise non-standard token could corrupt the accMfundPerShare accounting/user shares. There is also no explicit check preventing mFundToken itself from being added as a pool, which could create an undesirable economic feedback loop.
- If the contract's MFUND balance is insufficient, safeMfundTransfer sends only the available balance without reverting or recording the shortfall, and updates the user's rewardDebt as though the full amount had been paid; this causes the difference to be permanently lost (the user can no longer claim it) whenever reward liquidity is insufficient.
- In Memefund, the owner can set rebaseOracle to any address with no confirmation or delay (setRebaseOracle), and that address alone has full authority to increase or decrease the total token supply (rebase); if the rebaseOracle key is leaked or compromised, the entire circulating supply of MFUND — and hence the value of every holder's balance — can be manipulated arbitrarily (up to the MAXSUPPLY cap). No rate limit is enforced between two consecutive rebases.
- The two-step ownership pattern (transferOwnership/acceptOwnership) in Memefund correctly prevents ownership from being accidentally transferred to the wrong address; no issue was found in this part.

Contract address: 0x39360ac1239a0b98cb8076d4135d0f72b7fd9909
Project: XNFT (an NFT-collateralized lending protocol with a liquidation auction mechanism, in the style of a Compound fork with xTokens), pragma ^0.8.2, upgradeable (Initializable)
Issues and vulnerabilities:
- A critical vulnerability in the administrative withdraw function: this function is protected only by onlyAdmin but transfers an arbitrary amount of any arbitrary xToken directly to the admin address, with no restriction whatsoever relative to users' outstanding debt, locked collateral, or deposits mid-auction. Unlike withdrawAuctionIncome (which correctly limits withdrawal to addUpIncomeMap), this function can, if the admin key is compromised or misused, completely drain the entire balance of any token held by the contract — including user assets, such as ETH sent by auction participants in auction() that has not yet been repaid to the eventual winner or the original owner, or collateral awaiting withdrawal. This is effectively a full rug-pull capability for the admin.
- The claim function (an arbitrary call, via call, to any airdop address with any byteCode, gated only by onlyAdmin) is a very broad "escape hatch"; although restricted to the admin, if the admin key is leaked it is by itself sufficient to interact arbitrarily with any external contract (including approving the contract's tokens to an attacker's address), greatly widening the attack surface.
- A DoS risk in the auction mechanism: repayment to the previous bidder (doTransferOut, to liquidatedOrder.auctionAccount) for ETH-denominated pools is done via account.transfer(amount), which is capped at a 2300-gas stipend. A malicious bidder can place a bid through a contract whose receive/fallback function deliberately reverts or consumes more gas, registering their own address as auctionAccount; after that, every subsequent attempt to place a higher bid (auction), which requires automatically refunding the previous bid to this same malicious address, will always revert, and the auction is effectively locked forever with the attacker's bid left as the winner (a classic DoS pattern in online auctions with automatic refunds).
- The initialize function (OpenZeppelin's Initializable pattern) lacks a constructor with _disableInitializers() for the implementation contract; if this contract is deployed behind an upgradeable proxy, anyone could call initialize() directly on the raw implementation address and make themselves admin of that instance (not the main proxy). While the direct impact is usually limited to the implementation contract with no real users, this is a known best-practice gap that can become dangerous in more complex architectures (such as chained delegatecalls).
- Broad centralization of authority in the admin role: setting penalty rates (pledgerFineRate), reward rates (rewardFirstRate, rewardLastRate), auction duration, redeem protection, pausing any section (setPause), and adding/removing approved collections can all be changed instantly by a single admin address with no timelock or multisig; combined with no mandatory delay, this allows sudden changes to the protocol's economic rules to the detriment of users.
- In doTransferIn, for ERC20 tokens, a check that balanceAfter - balanceBefore == amount is performed to ensure the exact expected amount was received (appropriate protection against fee-on-transfer tokens); this part is implemented correctly.

Contract address: 0x3de669c4F1f167a8aFBc9993E4753b84b576426f
Project: Router / Pool (an automated market maker built on a two-sided liquidity pool, in the THORChain/Spartan style, on BSC), pragma 0.6.8
Issues and vulnerabilities:
- A critical and directly exploitable vulnerability in the public Pool.transferTo function: this function uses tx.origin instead of msg.sender as the source address for the token (LP) transfer ("_transfer(tx.origin, recipient, amount)"), with no restriction on the caller (e.g. onlyRouter). Since tx.origin always equals the original user account that initiated the transaction chain, any malicious contract can write a function that calls Pool(poolAddress).transferTo(attackerAddress, amount); if the victim holds an LP balance in that pool and simply interacts, through any transaction (even a completely unrelated one), with the attacker's contract, the attacker can directly transfer the victim's entire LP balance in that pool to their own address with no permission or related signature whatsoever. This is precisely the classic tx.origin-misuse vulnerability pattern (SWC-115), and here it is applied directly to the core asset-movement path rather than just a peripheral authentication check.
- In Router._handleTransferIn and _handleTransferOut, the low-level calls payable(WBNB).call{value:_amount}("") and payable(_recipient).call{value:_amount}("") are made with no check of the boolean success return value (unchecked low-level call); if this call fails (e.g. due to an expensive fallback or ETH rejection by _recipient), the function continues without reverting and the transaction is treated as successful even though the actual ETH/BNB was never delivered to the recipient — this can lead to permanent loss of funds or an accounting mismatch between the Router/Pool's internal state and the real balances.
- The swap/buy/sell/swapTo/buyTo/sellTo and addLiquidity*/removeLiquidity* functions have no slippage-protection parameter at all (such as minOutputAmount or a deadline); all of these operations are fully exposed to sandwich attacks (front-running/back-running by MEV bots) that extract value from ordinary users, since the output is calculated purely from the pool's instantaneous state, which an attacker can manipulate within the same block.
- The core pricing and liquidity-share logic (calcSwapOutput, calcLiquidityUnits, calcLiquidityShare, calcShare) is entirely delegated to an external UTILS contract (via DAO) that is not present in this flattened file; the correctness of the AMM formula (e.g. resistance to single-transaction flash-loan price manipulation) therefore cannot be verified, and the core economic-security risk of the protocol is shifted to that external contract.
- Router.migrateRouterData and migrateTokenData are protected by onlyDeployer, but the data read from oldRouter (itself an arbitrary address chosen by DEPLOYER) is written directly into mapToken_Pool and isPool with no validation at all; until purgeDeployer has been called, DEPLOYER could supply a fake oldRouter and register a completely malicious Pool address as the legitimate pool for a real token, hijacking and redirecting all swap/liquidity flow for that token. This is an accepted centralization risk prior to purging, but its significance is notable.

Contract address: 0x5bd997039FFF16F653EF15D1428F2C791519f58d
Project: NoMintRewardPool (a Harvest Finance farming reward pool, based on the Synthetix StakingRewards pattern), pragma 0.5.16

Contract address: 0xf244eA81F715F343040569398A4E7978De656bf6
Project: Nomad Bridge (a cross-chain messaging bridge; the Home, Replica, XAppConnectionManager, MerkleTreeManager, and QueueManager contracts — the "OPTICS" naming found in the code confirms Nomad's original project name), pragma >=0.6.11
Issues and vulnerabilities:
- An extremely critical vulnerability, architecturally matching the exact pattern behind one of the largest thefts in the history of cross-chain bridges: Replica.acceptableRoot only checks that confirmAt[_root] != 0 and that the current time has passed it; there is no exception whatsoever for the "empty-tree root." MerkleLib.branchRoot computes a Merkle root by combining an _item (leaf) with a _branch array (sibling hashes). If an attacker sets the _branch array equal to the well-known, publicly computable constants Z_0 through Z_31 (the library's precomputed empty-subtree hashes) and chooses index 0, then for any arbitrary "message" (_item) the attacker fabricates, the computed _calculatedRoot becomes exactly the root of a perfectly valid Merkle tree that contains only that one fabricated message, with every other branch empty. Because Replica.initialize records the initial committedRoot value (which is normally the initial/empty root of the Home tree at launch time) directly via confirmAt[_committedRoot] = 1, this "empty-tree root" effectively becomes registered as an acceptable root from the very moment the contract is deployed. The result is that any attacker can call prove (or proveAndProcess), supply any message of their choosing together with a proof made up of these same public Z_i constants, mark their forged message's status as Proven, and then execute it via process; this effectively bypasses the bridge's entire Merkle-proof verification mechanism and lets anyone forge an unlimited number of incoming messages (including arbitrary withdrawal instructions on the message-receiving contracts on the destination side). This is exactly the vulnerability class ("accepted zero/empty root") responsible for the largest known real-world cross-chain bridge hack, in which dozens of different addresses — including ordinary users who simply copied previously successful transactions — drained funds simultaneously and chaotically.
- Immediate, critical recommendation: if this contract is currently live/deployed with real assets, it should be paused (or set to a failed state) immediately. The correct fix is for acceptableRoot to explicitly reject the empty-tree root (or any default/unset value), or to use an explicit list of valid roots registered by the updater rather than simply "any non-zero value in confirmAt."
- update correctly verifies the updater's signature over the (oldRoot, newRoot) pair (_isUpdaterSignature) and sets confirmAt[_newRoot] with an optimisticSeconds delay (an optimistic challenge window); this part is reasonably designed (similar to an optimistic-rollup challenge period), but this delay provides no protection whatsoever against the vulnerable path above, which does not go through update at all and directly targets prove/process with the empty-tree root.
- The simple reentrancy guard (entered == 1 / entered = 0) in process is correctly implemented and prevents reentrant calls during execution of handle on the message recipient; this part alone is correct, but it is of no use against the main vulnerability above, which legitimately marks a forged message as Proven with no reentrancy required at all.
- The Double-Update mechanism (detecting a contradictory update from the updater in order to disable the bridge), implemented in Common/Home, is a reasonable defensive layer against a dishonest updater, but it operates independently of the empty-root vulnerability above and does not mitigate it.
